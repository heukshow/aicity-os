## 이번에 추가한 동작과 검증

### 결제 후 지속 저장과 프로세스 교체

`ad-commerce-payment-restart.test.js` 7개는 실제 디스크 SQLite와 서로 다른 Node 프로세스를 사용한다. 결제 제공자 응답은 합성 fixture다. 실제 PayPal API나 실제 결제는 사용하지 않는다.

- 주문 생성 응답 뒤 로컬 저장 직전에 시험 프로세스를 종료하고, 같은 멱등 요청으로 주문을 복구한다.
- 합성 제공자가 결제를 확정한 직후 응답을 받기 전에 프로세스를 종료한다. 로컬은 capturing과 예약을 보존한다.
- 새 프로세스에서 기존 제공자 주문/capture를 조회해 active로 복구한다. capture POST와 성공 이력은 한 번뿐이다.
- 예약 기한 뒤의 불명확한 capture도 새 청구 없이 복구한다.
- 두 위치 패키지의 파일·예약·기간이 함께 보존되며, 종료 시 두 예약을 함께 해제한다.
- 미결제 예약 만료는 제공자 호출 전에 차단하고, 이미 검증된 결제의 시작일을 재시작하지 않는다.

이는 운영 D1이나 실제 PayPal의 재시작 시험이 아니다. 원래 Sandbox 성공을 새 revision의 실제 결제 성공으로 인용하지 않는다.

### 승인·취소 복귀 연결

기존 서명 검증 라이브러리를 sandbox HTTP return 화면 및 결제 주문 payload와 연결했다. 설정된 returnOrigin이 있을 때만 서명된 return_url/cancel_url을 넣는다.

GET 복귀 요청은 결제·취소·예약 해제를 수행하지 않는다. 유효한 승인 복귀 화면의 스크립트는 같은 주문의 별도 접근키가 있어야 인증 POST를 보낸다. 취소·만료·접근키 누락 시 자동 capture하지 않는다. 오류 후 재확인 버튼은 새 capture가 아니라 reconcile 경로를 사용한다.

새 HTTP/스크립트 시험 9개가 이 경계를 확인한다. 스크립트는 VM 시험이며 실제 브라우저의 PayPal 자동 복귀를 새로 시험한 것은 아니다. 기존 실제-Sandbox runner는 여전히 수동 복귀 시험 도구다.

### PNG 검사 보완

압축 스트림 뒤 추가 IDAT 데이터와 두 번째 압축 스트림을 거부하도록 소비 바이트 수와 출력 상한을 검사했다. PNG의 알파 채널만 존재하고 전부 불투명한 로고도 거부한다. 지원 필터를 복원해 실제 투명 픽셀이 있는지 확인한다.

최종 PNG 시험 24개. 허용 범위는 일부 비인터레이스 8-bit PNG다. JPEG/WebP/팔레트·인터레이스 PNG가 지원된다는 뜻이 아니다. Node zlib를 사용하므로 운영 Worker로 옮길 때 nodejs_compat와 자원 한도를 별도 검증해야 한다.
